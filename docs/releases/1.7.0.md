# Rollfast 1.7.0

Rollfast 1.7.0 lets `ScheduleConfig` hold any schedule for a fixed number of updates, such as once per epoch, and adds
PyTorch's `CosineAnnealingLR` as `kind="cosine_annealing"`. Every fine-tuning builder accepts a `GradientPolicy`.
Optimizer defaults, state structure, and checkpoint format versions are unchanged.

## Schedules stepped per interval

PyTorch training loops usually step their scheduler once per epoch, so the learning rate is constant within an epoch.
`ScheduleConfig(steps_per_interval=k)` does the same for every schedule kind: the schedule is indexed by `count // k`,
and `total_steps`, `warmup_steps`, `decay_steps`, and `t_max` count intervals. A builder's `total_steps` argument fills
`ScheduleConfig.total_steps`, so it counts intervals too. `ScheduleConfig.total_updates` gives the run's length in
updates; the SWA start fraction, `OptimizerReport.total_steps`, and the default `preview_schedule` steps use it.

The index divides whichever clock `step_counter` selects. Under `"attempt"`, a skipped or rejected attempt still moves
toward the next interval; with accumulation, one count is one optimizer window. The default `k=1` returns the same
schedule function as 1.6.0.

## Cosine annealing

`ScheduleConfig(kind="cosine_annealing")` follows PyTorch's `CosineAnnealingLR` after the shared linear warmup:

```text
lr(i) = end_lr + (peak_lr - end_lr) * (1 + cos(pi * i / t_max)) / 2,   end_lr = end_lr_ratio * peak_lr
```

Unlike `warmup_cosine`, which reaches `end_lr` on the run's last slot, it reaches the floor only at slot `t_max`, which
defaults to the run after warmup. `t_max` sets another annealing period, and `after_end` selects whether the rate holds
the floor (`"clamp"`, the default) or keeps following the cosine back up as PyTorch does (`"cycle"`). Warmup and
`end_lr_ratio` keep the defaults shared by every kind, so matching PyTorch needs both set to zero:

```python
optim = rfft.adamw_from_plan(
    plan,
    base_lr=1e-3,
    weight_decay=5e-4,
    eps=1e-8,
    clip_global_norm=None,
    schedule=rfft.ScheduleConfig(
        kind="cosine_annealing",
        total_steps=epochs,
        steps_per_interval=updates_per_epoch,
        warmup_fraction=0.0,
        end_lr_ratio=0.0,
    ),
)
```

This reproduces `CosineAnnealingLR(T_max=epochs)` stepped once per epoch at every update, within float32 rounding.
Rollfast evaluates PyTorch's closed form, which PyTorch computes recursively, so the two can differ in the last bits.

`rollfast.schedules.cosine_annealing_schedule` and `rollfast.schedules.interval_schedule` provide both pieces for
optimizers used without a plan. See
[cosine annealing and per-interval schedules](../finetuning/configuration.md#cosine-annealing-and-per-interval-schedules).

## Gradient policies on every builder

Every `*_from_plan` builder accepts `gradient_policy`, as `compile_optimizer` does. Without it, the builders still clip
at `clip_global_norm` and skip nonfinite updates. `nonfinite="none"` applies every update, so a training loop that stops
on a nonfinite loss can check the returned loss on the host. `clip_global_norm` and `axis_name` remain shorthands; left
at their defaults they defer to the policy, and otherwise they must match it.

## Compatibility

Rollfast's base requirements are unchanged: Python 3.12+, JAX 0.6.2+, and Optax `>=0.2.8,<0.3.0`. The checkpoint schema
and array format remain at version 1.

Review these changes when upgrading:

- With `steps_per_interval` greater than 1, `total_steps`, `warmup_steps`, `decay_steps`, and a builder's `total_steps`
  count intervals, while `OptimizerReport.total_steps` and SWA's `start_fraction` count updates. Nothing changes with
  the default `steps_per_interval=1`.
- `ScheduleKind` no longer lists `"custom"`, which `ScheduleConfig` always rejected. Only type checking is affected.
- Checkpoint manifests record `steps_per_interval`, `t_max`, and `after_end`. Manifests written by 1.6.0 restore under
  strict validation with their defaults; 1.6.0 cannot restore manifests written by 1.7.0.

## Known limitations

- The fine-tuning builders do not accept a callable Optax schedule; a callable would make manifests non-serializable and
  leave strict restores unable to compare schedules. Use the standalone optimizers with
  `rollfast.schedules.interval_schedule` instead.
- A short last epoch is the caller's responsibility: pass the number of batches the loader yields per epoch as
  `steps_per_interval`.
- Passing `clip_global_norm=1.0` explicitly together with a `gradient_policy` that clips differently cannot be told
  apart from the default; the policy wins.
- The Schedule-Free wrappers in `rollfast.schedules`, such as `schedule_free_kron`, build their own WSD schedule from
  `total_steps` and do not hold it per interval.
- The limitations listed in the [1.6.0 notes](1.6.0.md#known-limitations) remain.
