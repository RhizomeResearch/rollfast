# Rollfast 1.3.0

Rollfast 1.3.0 makes low-precision fine-tuning explicit. Every compiled bundle reports which precision mode its policy
resolves to, the composite steps honor master parameters, loss scaling, and stochastic parameter rounding together, and
a step state can be checkpointed and resumed exactly. The public v1 optimizer interface, optimizer defaults, and
checkpoint format versions remain in place.

## Precision modes

`bundle.report.precision` names one of four modes: `full_precision`, `master_mixed_precision` (BF16/FP16 model copy with
float32 masters), `master_free_stochastic` (BF16 parameters updated through stochastic rounding), and
`master_free_nearest`. The report also states master and moment storage, how BF16 moments round, and the parameter and
master bytes, and the manifest records it as `resolved_precision`.

Float32 masters keep every residual update, so their cast back to the model dtype stays round-to-nearest. The new
`PrecisionConfig.parameter_rounding="stochastic"` replaces the masters when their four bytes per parameter matter: each
update is added in float32 and rounded stochastically back to BF16, with keys from the checkpointed
`RNGStreams.stochastic_rounding` stream. The stream advances only with applied updates, and parameter partitions fold
their axis index into the key while replicas share it.

The `bf16_mixed_precision`, `bf16_master_free_precision`, and `fp16_mixed_precision` presets name the supported
combinations, and every `*_from_plan` builder accepts `precision=`. See
[low-precision fine-tuning](../finetuning/precision.md) for the mode table, the helpers that honor each field, and
troubleshooting.

## Composite steps

`FineTuneStepState`, `RNGStreams`, and `StepCounters` are registered PyTrees, so `make_finetune_update_step` runs under
`jax.jit` and `jax.lax.scan`. It now supports gradient accumulation, one call per microbatch, discarding a window that
contains a nonfinite microbatch. `make_finetune_sam_step` adds SAM/ASAM with the same precision handling. Step info
reports `grads_finite` separately from `update_applied`.

A step rejects an update whose result overflows the visible dtype, even when the gradients are finite; such a rejection
does not lower a dynamic loss scale, which now backs off only on gradient overflow and stays within
`[min_loss_scale, max_loss_scale]`. With declared collective axes, all parameter partitions agree on accepting or
rejecting the update.

`make_step_state_checkpoint` and `step_state_from_checkpoint` store and rebuild the optimizer state, masters,
accumulation record, model state, loss scale, RNG streams, and counters. See
[state and checkpoints](../finetuning/state_and_checkpoints.md#composite-step-state) and
[the runnable example](../../examples/finetuning/low_precision.py).

## Numerical fixes

- Global-norm clipping and SAM norms promote to float32 before squaring; FP16 gradients above 256 previously overflowed
  the norm. The clip scale is applied in float32.
- `make_sam_step` and the `LossBundle` steps accumulate microbatch sums in the accumulation dtype; a BF16 running sum of
  ones previously stopped at 256. The perturbed SAM pass now evaluates the model at the trainable dtype.
- GaLore and APOLLO project and square BF16 gradients in float32.
- BF16 stochastic rounding keeps every NaN a NaN.
- Master parameters keep complex values and the precision of float64 leaves, so complex fine-tuning plans can keep
  masters.

## Compatibility

Rollfast's base requirements are unchanged: Python 3.12+, JAX 0.6.2+, and Optax `>=0.2.8,<0.3.0`.

Existing checkpoints remain loadable. `RNGStreams` and `StepCounters` keep their field-based array checkpoint schema
despite their PyTree registration, and manifests written before `parameter_rounding`, `min_loss_scale`, and
`max_loss_scale` existed compare as if they held the defaults.

Review these behavior changes when upgrading:

- Master-aware steps return `None` for master parameters when the policy keeps none, instead of a copy of the visible
  parameters. The copy changed the state structure after the first call, so a jitted step recompiled and checkpoint
  templates built before training stopped matching. When the policy keeps masters, pass them, and any loss-scale state,
  from the first call, or use `init_finetune_step_state` with the composite steps.
- `PrecisionConfig` and the builders reject settings that previously had no effect: non-floating dtypes, a non-float32
  `update_compute_dtype`, sub-float32 master dtypes, an `accumulation_dtype` that differs from
  `AccumulationConfig.accumulate_dtype`, a non-float32 `preconditioner_dtype` outside `kron_adam`, and quantized moments
  whose `moment_dtype` differs from the fallback dtype.
- Direct-parameter helpers such as `make_update_step` warn when the bundle keeps masters or scales the loss, and reject
  stochastic parameter rounding. `make_state_checkpoint` warns when masters are kept but omitted.
- Composite accumulation requires `GradientPolicy(nonfinite="skip")`, the default.
- `init_finetune_step_state` checks supplied masters, and its default accumulation record no longer holds a gradient
  buffer.

## Known limitations

- Precision is configured per bundle, not per parameter group, and first and second moments share `moment_dtype`.
- `make_finetune_update_step` does not accept `LossBundle` losses; the `LossBundle` steps update parameters directly.
- `cast_back` supports only `"nearest"`.
- Multi-device behavior is verified on forced multi-device CPU; accelerator validation is not part of this release.
- The averaging and Schedule-Free limitations listed in the [1.2.0 notes](1.2.0.md#known-limitations) remain.
